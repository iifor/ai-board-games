# 狼人杀 12 人玩法拓展项目约束

## 目标

本文件约束后续实现者如何在现有项目结构内开发“预女猎守（12人）”和“白狼王守卫（12人）”，避免规则、展示、回放和后台配置漂移。

## 项目结构约束

实现必须遵循现有 monorepo 分层：

- 后端规则、工作流、AI 行动、死亡结算：`packages/server/modules/werewolf`。
- 狼人杀角色和模式管理：`packages/server/modules/werewolf-config`。
- 默认种子数据：`packages/server/db/seed.ts` 及服务端启动 seed 流程。
- 共享事件类型、播放字段和 schema：`packages/shared`。
- C 端展示、socket 消费和回放合并：`packages/client/src/features/werewolf` 及 v2 复用入口。
- B 端配置、历史详情和调试展示：`packages/admin`。
- 项目文档：`docs/`。

不得把完整功能堆入单个大文件。新增逻辑应优先复用现有模块边界。

## 预计改动范围

### 后端

- 新增或补齐白狼王默认角色配置。
- 新增“白狼王守卫（12人）”默认模式。
- 修正“预女猎守（12人）”模式说明与阵容一致性。
- 扩展白狼王自爆带人 AI 输出、合法性校验和结果落盘。
- 复用现有 `selfDestruct`、`deathResolution`、`hunter_shot`、`sheriff_badge` 和胜负检查流程。
- 生成稳定公开事件，确保实时播放和历史回放一致。

### 共享类型

- 若现有事件类型不足以表达“白狼王自爆带人”，应扩展稳定 payload 类型。
- 类型字段应表达自爆者、被带走目标、原因、是否成功带人。
- 不允许用大量 `any` 或 `as any` 掩盖协议不清晰问题。

### C 端

- 模式选择能展示两个 12 人模式并正确计算人数。
- 座位、事件日志、死亡状态和回放能展示白狼王自爆及带走目标。
- C 端只合并服务端事件，不自行判断自爆是否合法或目标是否死亡。

### B 端

- 模式管理能显示新角色、新模式、人数、阵容和胜利条件。
- 历史详情能正确展示新模式名称和角色阵容。
- 调试视图若展示相关事件，不得泄露不应公开的私密信息到 C 端协议。

### 文档

实现后必须同步更新：

- `docs/project-workflow.md`
- `docs/project-server.md`
- `docs/project-client.md`
- `docs/project-admin.md`
- `docs/project-shared.md`

## 数据与迁移约束

- 默认不新增数据库表。
- 现有数据库非空时，新增默认角色和默认模式必须能自动补齐，或提供明确迁移路径。
- 如果只改 `DEFAULT_WEREWOLF_ROLES` / `DEFAULT_WEREWOLF_MODES`，必须确认当前 seed 流程是否会覆盖非空库；若不会，需要实现安全补齐。
- 补齐逻辑不得覆盖用户在后台手动修改过的现有模式，除非明确只修正系统默认模式的已知错误文案。

## 规则边界

- 前端不得决定死亡、胜负、技能合法性、行动目标合法性。
- 后端不得信任 AI 输出；所有目标、行动类型和 actor 资格都必须服务端校验。
- 白狼王带人必须进入统一死亡链，不能直接修改玩家死亡状态后跳过后续流程。
- 自爆中止当天普通发言和放逐投票，但不能跳过死亡链、胜负检查或赛后流程。
- 实时播放和精确回放必须消费同一最终事件语义。

## 质量约束

- 先补失败测试，再实现最小代码改动。
- 重点覆盖 workflow 层测试，而不是只测 UI。
- 不引入不必要的新依赖。
- 不重写整个狼人杀 workflow。
- 不破坏 `standard-12`、`guard-12`、警长、女巫、守卫、猎人、MVP 和赛后感言流程。

## 修改前必须确认

实现者开始编码前必须说明：

1. 当前目录结构判断。
2. 本次涉及前端、后端、数据库还是共享类型。
3. 会新增哪些文件。
4. 会修改哪些文件。
5. 每个文件的职责。
6. 是否复用已有模块，还是新增模块。
